## Общее для всех частей

### Цель

У каждой категории одежды появляются внутренние свойства: слот, уровень отрисовки, группа замены и раздел каталога. Они описаны в одном конфиге в датасете, проверяются при каждой сборке и доходят до `repository:api`. Каталог и кукла пока их не используют.

### Принятые решения

- Конфиг — один файл `temporary-dataset/src/main/assets/categories.json`, рядом с папкой `cloth-src`, а не внутри неё: так он не попадает в список категорий.
- Ключи категорий — имена папок на русском. id уровней, групп, разделов и значения слотов — латиница.
- Уровни — упорядоченный массив id, числа не хранятся. Позиция уровня (с 1) — его порядок отрисовки.
- Группа необязательна: без неё категория образует собственную группу с лимитом 1. Явные группы описаны в `groups` с лимитом.
- Конфиг, его разбор и модели живут только в `:temporary-dataset`. Остальные модули видят данные только через `repository:api`.
- Разбор в рантайме — встроенный `org.json`, без новых зависимостей. Рантайм доверяет проверке сборки, но на несогласованность падает с исключением, а не подставляет значения по умолчанию.
- Проверка при сборке — convention-плагин в `build-logic`, подключён только к `:temporary-dataset` (часть 2).
- z-index, порядок надевания и замена по лимиту в этот план не входят: это логика куклы, у неё будет свой план.
- Заправленное, крепления и аксессуары не входят (см. «Вне рамок» в z-index.md).

### Требуют подтверждения

- Лимит нательного (2) и отдельный уровень рубашек взяты из z-index.md, где они помечены как неподтверждённые.
- Порядок категорий в репозитории меняется с алфавитного на порядок из конфига (по разделам). В плоском каталоге это видно сразу.
- «Только в одном модуле»: код проверки лежит в `build-logic`, а не в `:temporary-dataset`. Если нужно строго внутри модуля, задача переезжает в `temporary-dataset/build.gradle.kts`, логика не меняется.

### Модули

```
:temporary-dataset   categories.json, разбор, модели TD*            (часть 1)
build-logic          плагин dressdoll.clothing.dataset, валидатор   (часть 2)
:repository:api      модели слота, уровня, группы, раздела          (часть 3)
:repository:impl     маппинг TD* → api                              (часть 3)
```
